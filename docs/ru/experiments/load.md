# Нагрузочное тестирование HTTP-запроса

Узел [[ui:exp.node.http]] может отправить свой запрос много раз подряд, по профилю с
заданным числом запросов в секунду, по многу сразу, — и измерить, что вернулось:
процентили задержки, ошибки, достигнутый темп. Пороги решают, проходит ли шаг, а кнопка
[[ui:exp.compare]] ставит эти числа рядом с числами предыдущего запуска.

Нагрузка — это настройка узла, а не отдельный узел: остальная часть эксперимента —
эмуляторы, реле помех, другие ветки — работает вокруг неё как обычно.

## Как включить нагрузку {#turn-on}

1. Выберите узел [[ui:exp.node.http]] и заполните его запрос.
2. В его свойствах установите флажок [[ui:exp.loadOn]].
3. Выберите [[ui:exp.loadShape]] и задайте его числа. График под ними,
   [[ui:exp.loadChart]], рисует темп и показывает, сколько всего получается запросов и за
   сколько секунд.
4. Укажите в поле [[ui:exp.loadConcurrency]], сколько запросов может быть в пути
   одновременно.
5. Добавьте или измените [[ui:exp.thresholds]].
6. Запустите эксперимент.

По умолчанию нагрузка — профиль [[ui:exp.loadShape.ramp]] от 0 до 100 запросов в секунду
за 30 000 мс, 32 одновременно, с двумя порогами: [[ui:exp.metric.p95_ms]] < 500 мс и
[[ui:exp.metric.error_rate]] < 1 %.

**Нагрузка заменяет серию отправок и повтор при ошибке.** Если её включить, они
выключаются, а узел с нагрузкой и любой из них отклоняется (`node.load_alone`):
неудачный запрос подсчитывается, а не повторяется. Под нагрузкой может работать только
HTTP-запрос (`node.load_unsupported`).

**Запрос читается один раз.** Его шаблоны подставляются в начале шага, поэтому все
запросы нагрузки одинаковы: `{{counter}}` и `{{uuid}}` принимают одно значение для всех.
См. [шаблоны](data.md#templates).

**Один клиент на всю нагрузку.** Запросы делят банку cookie запуска, когда установлен
флажок [[ui:exp.cookies]], и одну память Digest, так что одного вызова сервера хватает
на все запросы. Каждый запрос ограничен тайм-аутом самого узла.

**Инспектор получает выборку:** не больше одного обмена каждые 100 мс, чтобы нагрузка
не заваливала [[ui:dock.inspector]].

## Профили {#profiles}

| [[ui:exp.loadShape]] | Настройки | Темп во времени |
| --- | --- | --- |
| [[ui:exp.loadShape.constant]] | [[ui:exp.loadRate]], [[ui:exp.loadDuration]] | один и тот же темп всё время |
| [[ui:exp.loadShape.ramp]] | [[ui:exp.loadFrom]], [[ui:exp.loadTo]], [[ui:exp.loadDuration]] | по прямой от одного темпа к другому |
| [[ui:exp.loadShape.steps]] | [[ui:exp.loadFrom]], [[ui:exp.loadStepBy]], [[ui:exp.loadEvery]], [[ui:exp.loadSteps]] | первый темп, затем на каждой ступени на шаг больше; каждая ступень длится одинаково |
| [[ui:exp.loadShape.spike]] | [[ui:exp.loadBase]], [[ui:exp.loadPeak]], [[ui:exp.loadAt]], [[ui:exp.loadSpikeFor]], [[ui:exp.loadDuration]] | базовый темп, с заданного момента на время — пиковый, затем снова базовый |
| [[ui:exp.loadShape.poisson]] | [[ui:exp.loadRate]], [[ui:exp.loadDuration]] | приходы в случайные моменты, в среднем с заданным темпом |

При смене профиля сохраняется то, что можно перенести: сколько длится нагрузка и
наибольший темп, которого она достигает.

### Ограничения {#limits}

| Настройка | Диапазон |
| --- | --- |
| [[ui:exp.loadRate]] у профилей [[ui:exp.loadShape.constant]] и [[ui:exp.loadShape.poisson]], [[ui:exp.loadPeak]] | 0,1–100 000 запросов/с |
| [[ui:exp.loadFrom]], [[ui:exp.loadTo]], [[ui:exp.loadBase]] | 0–100 000 запросов/с |
| Каждая ступень профиля [[ui:exp.loadShape.steps]], включая последнюю | 0–100 000 запросов/с; шаг может быть отрицательным |
| [[ui:exp.loadDuration]], [[ui:exp.loadEvery]] | 100–300 000 мс |
| [[ui:exp.loadSteps]] | 1–100, а все ступени вместе — не больше 300 000 мс |
| Всплеск | дольше 0 мс и заканчивается до конца длительности |
| [[ui:exp.loadConcurrency]] | 1–512 |
| [[ui:exp.thresholds]] | не больше 16, каждое значение — число, 0 или больше |

Профиль, который в сумме не даёт ни одного запроса, отклоняется
(`load.nothing_planned`). Диапазоны темпа — те же, что у
[нагрузочного потока HTTP](../protocols/http.md).

Профиль может длиться столько же, сколько весь запуск, 300 с, — но
[ограничение времени](flow.md#limit) запуска учитывает все шаги, так что оставьте запас
для остального эксперимента.

### Сколько запросов {#planned}

Запросы профиля — это его темп, сложенный по времени:

| Профиль | Запросов |
| --- | --- |
| [[ui:exp.loadShape.constant]], 100/с в течение 1000 мс | 100 |
| [[ui:exp.loadShape.ramp]], 0 → 100/с за 2000 мс | 100 |
| [[ui:exp.loadShape.steps]], от 10/с с шагом 10/с, 3 ступени по 1000 мс | 60 (10 + 20 + 30) |
| [[ui:exp.loadShape.spike]], 10/с со всплеском до 100/с с 1000 мс на 500 мс, всего 2000 мс | 65 |
| [[ui:exp.loadShape.poisson]], 200/с в течение 10 000 мс | в среднем 2000 |

## Расписание {#schedule}

n-й запрос назначается на тот момент, когда счёт профиля достигает n; первый — сразу.
Каждый момент вычисляется от начала нагрузки, поэтому запоздалое пробуждение никогда не
сдвигает следующие запросы, и темп, описанный профилем, — это и есть запрошенный темп.

Профиль [[ui:exp.loadShape.poisson]] выбирает промежутки между приходами случайно, из
seed запуска: тот же seed даёт те же моменты, поэтому случайную нагрузку можно повторить
в точности. См. [seed](runs.md#seeds).

**Пропущенные запросы.** В пути одновременно не больше запросов, чем задано в поле
[[ui:exp.loadConcurrency]]. Когда все они ещё ждут ответа, следующий запрос ждёт
свободного места. Если он ушёл бы больше чем через 50 мс после своего момента, его не
отправляют с опозданием: он пропускается и считается пропущенным — вместе со всеми
запросами, срок которых наступил за это время, — и нагрузка продолжается с первого
запроса, который ещё успевает вовремя. Много пропущенных запросов означает, что сервер
или значение [[ui:exp.loadConcurrency]] не поспевали за профилем.

## Во время выполнения {#progress}

Раз в секунду лента показывает шаг как [[ui:exp.load]] — с прошедшими секундами,
отправленными запросами, темпом за последнюю секунду, p95 на текущий момент и
неудачными запросами. Кнопка [[ui:common.stop]] сразу завершает нагрузку и бросает
запросы, которые ещё в пути; сбой в другой ветке завершает её в течение секунды.

## Что измеряется {#metrics}

После последнего ответа у шага есть измерения; они хранятся в его последнем событии на
ленте и в [отчёте о запуске](runs.md#report):

| Измерение | Что это |
| --- | --- |
| planned | запросы, которые даёт профиль ([[ui:exp.loadShape.poisson]] — в среднем) |
| sent | запросы, получившие ответ или не прошедшие |
| ok | получили ответ со статусом 2xx |
| failed | любой другой статус или вообще без ответа |
| missed | срок наступил, когда все места были заняты, и запрос пропущен |
| rps | отправленных запросов в секунду: sent ÷ длительность профиля — или ÷ время до отправки последнего запроса, если оно больше |
| error_rate | failed в % от sent |
| min, mean, max | самый быстрый, средний и самый медленный запрос, мс |
| p50, p90, p95, p99 | задержка, которой не превысили 50, 90, 95 и 99 % запросов, мс |
| received_bytes | всего получено байт тела |
| statuses | запросы по статусу (`200`, `503`), а без статуса — по причине (`timeout`, `refused`, `reset` …) |
| seconds | каждая секунда профиля: отправлено запросов, из них неудачных, их средняя задержка |
| histogram | запросы по задержке: до 1, 2, 5, 10, 20, 50, 100, 200, 500, 1000, 2000, 5000, 10 000 мс и медленнее |

Задержка запроса считается от отправки до чтения всего ответа, а неудачный запрос
учитывается со временем, которое ушло на неудачу. Процентили берутся из логарифмических
корзин шириной 1 % и отличаются от истинного значения не больше чем на 0,5 %, сколько
бы ни шла нагрузка.

## Пороги {#thresholds}

Порог — это строка из полей [[ui:exp.thresholdMetric]], [[ui:exp.thresholdOp]] и
[[ui:exp.thresholdValue]]; кнопка [[ui:exp.thresholdAdd]] добавляет ещё один.

| [[ui:exp.thresholdMetric]] | В чём измеряется |
| --- | --- |
| [[ui:exp.metric.p50_ms]], [[ui:exp.metric.p90_ms]], [[ui:exp.metric.p95_ms]], [[ui:exp.metric.p99_ms]] | мс |
| [[ui:exp.metric.mean_ms]], [[ui:exp.metric.max_ms]] | мс |
| [[ui:exp.metric.error_rate]] | % от отправленных запросов |
| [[ui:exp.metric.rps]] | достигнутые запросы в секунду |
| [[ui:exp.metric.missed]] | запросы |

Поле [[ui:exp.thresholdOp]] принимает одно из значений `<`, `≤`, `>`, `≥`. Несколько
типичных порогов:

| [[ui:exp.thresholdMetric]] | [[ui:exp.thresholdOp]] | [[ui:exp.thresholdValue]] | Шаг не проходит, когда |
| --- | --- | --- | --- |
| [[ui:exp.metric.p95_ms]] | `<` | 300 | каждый двадцатый запрос или чаще длился 300 мс или дольше |
| [[ui:exp.metric.error_rate]] | `<` | 1 | не прошёл 1 % запросов или больше |
| [[ui:exp.metric.rps]] | `≥` | 180 | сервер не смог принять 180 запросов в секунду |
| [[ui:exp.metric.missed]] | `≤` | 0 | пришлось пропустить хотя бы один запрос |

В файле порог записывается как `{ "metric": "p95_ms", "op": "lt", "value": 300 }`;
метрики — `p50_ms`, `p90_ms`, `p95_ms`, `p99_ms`, `mean_ms`, `max_ms`, `error_rate`,
`rps` и `missed`, сравнения — `lt`, `le`, `gt` и `ge`.

Пороги проверяются после последнего ответа, по порядку. Шаг не проходит на первом
невыполненном пороге (`load.threshold`) — в сообщении будут порог и измеренное
значение, — и запуск не проходит вместе с ним. Без порогов нагрузка проходит, что бы она
ни намерила. Если нагрузку раньше времени завершил сбой другой ветки, это сбой запуска, а
не порога.

## Результат {#result}

Когда шаг проходит, лента подводит итог: запросы, темп, p95 и доля неудачных. Выберите
узел: в его свойствах показан раздел [[ui:exp.loadResult]] —

- каждый порог, ✓ [[ui:exp.thresholdHeld]] или ✕ [[ui:exp.thresholdBroken]], с
  измеренным значением;
- [[ui:http.sent]], [[ui:exp.loadRps]], [[ui:exp.loadErrors]] с их долей,
  [[ui:http.missed]];
- [[ui:http.p50]], [[ui:http.p90]], [[ui:http.p95]], [[ui:http.p99]],
  [[ui:http.avg]], [[ui:http.max]];
- [[ui:exp.loadPerSecond]]: запросы каждой секунды, неудачные — красным, а их средняя
  задержка — линией;
- [[ui:exp.loadLatencies]]: сколько запросов сколько длились;
- статусы и причины, у каждого — количество.

Командная строка печатает те же числа и вердикт по каждому порогу; см.
[`signallab run`](../automation/cli.md#cli-run).

## Сравнение двух запусков {#compare}

1. Запустите эксперимент два раза или больше.
2. На ленте нажмите [[ui:exp.compare]]. Кнопка появляется, когда запуск сохранил свой
   отчёт, и недоступна, пока идёт запуск.
3. Последний запуск — [[ui:exp.compareAfter]], предыдущий — [[ui:exp.compareBefore]]; в
   любом из списков можно выбрать другой запуск.

В списках — запуски этого эксперимента (по его имени) из отчётов в папке данных, новые
сверху, не больше 50: у каждого дата и время, чем он закончился, и его seed. Запуски из
командной строки там тоже есть, если она использовала ту же папку данных. Переименование
эксперимента начинает новую историю.

Для каждого шага с нагрузкой, сопоставленного по узлу, таблица показывает каждую
метрику — [[ui:exp.compareBefore]], [[ui:exp.compareAfter]] и
[[ui:exp.compareChange]] — в единицах измерения и в %. Изменение в худшую сторону на 5 %
или больше — медленнее, больше ошибок, больше пропущенных запросов, ниже темп — это
регрессия, она выделяется красным; переход от нуля к чему-то тоже считается. Под
таблицей — вердикт каждого порога в обоих запусках. Шаг с нагрузкой, который есть только
в одном из запусков, помечен [[ui:exp.compareOnlyBefore]] или
[[ui:exp.compareOnlyAfter]], без изменений. Для запусков без шагов с нагрузкой показано
[[ui:exp.compareNoLoad]].

Из скрипта [`experiment_runs`](../api/commands.md#experiment_runs) перечисляет запуски,
а [`experiment_compare`](../api/commands.md#experiment_compare) сравнивает два из них по
имени файла отчёта; `signallab mcp` предлагает то же самое ассистенту
([MCP](../automation/mcp.md)).

## Проверки после нагрузки {#checks-after}

Нагрузка не оставляет собственного ответа: её измеряют, а не проверяют. Проверке или
узлу [[ui:exp.node.extract]] после неё нужен на каждом пути перед ними другой запрос без
нагрузки, иначе эксперимент не запустится (`graph.needs_http`). Чтобы проверить один
ответ API под нагрузкой, поставьте обычный [[ui:exp.node.http]] после нагрузки или в
параллельной ветке рядом с ней.

Кнопка [[ui:exp.sendNow]] на узле под нагрузкой отправляет его запрос один раз.
