# UDP と TCP

生の UDP と TCP には、専用の画面はありません。プロジェクター、メディアサーバー、センサーなど、独自のテキストまたはバイナリのプロトコルを持つデバイスに使うもので、いくつかの場所に登場します。

| やりたいこと | 使うもの |
| --- | --- |
| データグラムや TCP メッセージをステップとして送信し、応答を待つ | [実験のステップ](#experiments) |
| 再送信するデータグラムを保存する、またはキャプチャしたものを再生する | [UDP シグナル](#signals) |
| スクリプトから 1 件のデータグラムを送信する | [`signallab send udp`](#cli) |
| 多数のホスト、ブロードキャストアドレス、マルチキャストグループに一度に送信する | [ブロードキャスト](broadcast.md)画面 |
| サーバーや回線にトラフィックで負荷をかける | [ストーム](#storm) |
| ホストで開いている TCP ポートを調べる | [スキャナー](#scanner) |
| デバイス側を演じる | [UDP または TCP デバイス](#emulators)のエミュレーター |
| 両端の間のネットワークを劣化させる | [劣化リレー](#impairment) |

OSC は UDP データグラムで運ばれるフォーマットで、専用のページがあります。[OSC](osc.md)を参照してください。

## ペイロード {#payloads}

生のペイロードを書く場所では、どこでも次の 2 種類のいずれかになります。

| 種類 | 送信される内容 | 例 |
| --- | --- | --- |
| テキスト | 入力したとおりの文字を UTF-8 で送信します。終端文字も改行も追加されません。行プロトコルでは、テキストに行末を含める必要があります。 | `PING` |
| hex バイト列 | 16 進数 2 桁の組で書いたバイト列をそのまま送信します。組の間のスペース、`:`、`-`、`,` と、先頭の `0x` は使えます。 | `de ad be ef`、`DEADBEEF`、`0xde,0xad` |

1 つのデータグラムに載せられるのは最大 65,507 バイトです。16 進数の桁数が奇数の場合や、桁が 1 つもない場合は、何も送信される前にエラーになります。

::: info
UDP には配達確認がありません。「送信済み」は、データグラムがこのマシンから出たという意味で、誰かが受信したという意味ではありません。デバイスが受け取ったかどうかを知るには、その応答を待ってください。
:::

## 送信先 {#destinations}

送信先は、IP アドレスとポート、またはホスト名とポートです。`192.0.2.20:9000`、`[2001:db8::20]:9000` (IPv6 アドレスは角括弧で囲みます)、`projector.local:9000` のようにします。これは、UDP ステップの宛先、OSC の宛先、UDP シグナル、`signallab send udp` と `signallab send osc`、[ブロードキャスト](broadcast.md)のリスト、[ストーム](../tools/storm.md)の宛先、TCP ステップのホストのすべてに当てはまります。

ホスト名は、使うたびに名前解決されます。IPv4 アドレスがあればそれを使います。そのため、システムが最初に返すアドレスが `::1` であっても、`localhost` は `127.0.0.1` で待ち受けるサービスに届きます。IPv6 アドレスしかない名前には、IPv6 ソケットから届きます。名前解決できない名前は `Cannot resolve …` で失敗し、ポートのない宛先や、どちらの形式でもない宛先は `… is not a valid address` で失敗します。サービスが*待ち受ける*アドレス (モニター、待機、エミュレーターのもの) は、常に `IP:port` です。

## 実験での使い方 {#experiments}

| ステップ | 動作 |
| --- | --- |
| [[ui:exp.node.udp]] | [[ui:exp.payload]] をテキストとして [[ui:common.target]] に送信します。宛先は `IP:port` または `host:port` ([上記](#destinations)) で、カンマで区切った複数の宛先には、それぞれにデータグラムが送られます。[[ui:exp.expectReply]] を使うと、[[ui:exp.replyOn]] から送信し、同じステップ内でそこに届く応答を待ちます。[詳細](../experiments/nodes.md#node-udp) |
| [[ui:exp.node.wait_udp]] | [[ui:exp.listenOn]] (`IP:port`) で待ち受け、ペイロードが一致するデータグラムを待ちます。[詳細](../experiments/nodes.md#node-wait_udp) |
| [[ui:exp.node.tcp]] | [[ui:exp.host]] と [[ui:exp.port]] に接続し、[[ui:exp.payload]] をテキストとして書き込み、応答を 250 ms 待ち受けてから閉じます。ステップには、返ってきたバイト数は表示されますが、その内容は表示されません。[詳細](../experiments/nodes.md#node-tcp) |

UDP のペイロードと宛先、TCP のホストとペイロード、待機のパターンには `{{templates}}` が使えます。そのため、データグラムに実行の ID や、前のステップで抽出した値を含められます。[データとテンプレート](../experiments/data.md)を参照してください。

### データグラムの照合 {#matching}

[[ui:exp.node.wait_udp]] と [[ui:exp.node.udp]] の応答は、ペイロードでデータグラムを選びます。

| [[ui:exp.waitMode]] | データグラムを受け取る条件 |
| --- | --- |
| [[ui:exp.mode.any]] | 常に。最初に届いたもの |
| [[ui:exp.mode.contains]] | ペイロードをテキストとして読んだとき、パターンを含む |
| [[ui:exp.mode.regex]] | ペイロードをテキストとして読んだとき、正規表現に一致する |
| [[ui:exp.mode.hex]] | バイト列が、hex で書いたパターンのバイト列を含む |

一致した内容は、ステップの変数 ([[ui:exp.replyVariable]]。名前を変えなければ `reply`) に保持されます。含まれるのは、`text`、`hex` (先頭の 1024 バイト)、`bytes` (サイズ)、`from` (送信元の `IP:port`)、`ms` (かかった時間)、`match` (見つかったテキストやバイト列、または正規表現の最初のグループ) です。

待機は、ステップに到達したときではなく実行の開始時に待ち受けを始めるので、非常に速い応答も取りこぼしません。受け取るのは、その経路上の最後の送信より後に届いたものだけです。

### 上限と既定値 {#limits}

| 設定 | 既定値 | 範囲 |
| --- | --- | --- |
| TCP ステップの [[ui:common.timeoutMs]] (接続、書き込み、応答の合計) | 4000 ms | 1〜120,000 ms |
| 待機または応答の [[ui:exp.waitTimeout]] | 2000 ms | 1〜120,000 ms |
| UDP ペイロード | — | 最大 65,507 バイト |
| 待ち受けアドレス | — | ポート付きの `IP:port`。応答の [[ui:exp.replyOn]] はポート 0 (空いている任意のポート) も使えます |

インスペクターでは、UDP ステップのデータグラムはソース `broadcast` (ステップが応答を待つ場合は `experiment`) として表示され、待機のポートに届いたすべてのデータグラムはソース `experiment-wait` として表示されます。TCP ステップは、ソース `experiment` の 2 つの `tcp` フレームとして表示されます。書き込んだペイロードと、応答があった場合は読み取った応答です。タイムラインの項目には、送信した内容と応答の大きさが表示されます。

## シグナル {#signals}

ライブラリの [[ui:sig.tr.udp]] シグナルは、宛先と、テキストまたは hex バイト列のペイロードです。[[ui:nav.signals]] から、またはどの画面からでも <kbd>Ctrl</kbd>+<kbd>K</kbd> で送信できます。宛先にはホスト名も使えます。

インスペクターが完全に保持したデータグラムは、どれでもシグナルにできます。[[ui:sig.fromFrame]] は、[[ui:sig.capturedFolder]] フォルダーに hex の UDP シグナルを作り、まったく同じバイト列を再生します。送信されたフレームの場合はそのフレームの宛先へ、受信したフレームの場合はそれを受け取ったアドレスへ送ります (受信したアドレスがすべてのアドレスだった場合は、このコンピューターです)。TCP のチャンクはストリームの一部なので、シグナルにできません。[シグナル](../tools/signals.md)と[インスペクター](../tools/inspector.md#save-as-signal)を参照してください。

テキストの UDP シグナルは、[[ui:exp.node.udp]] ステップとして実験に追加できます。hex のシグナルは、ステップがテキストを送信するため、追加できません。

## コマンドラインから {#cli}

`signallab send udp` は、1 件のデータグラムを送信します。

```bash
signallab send udp 127.0.0.1:9000 --text "PING"
signallab send udp 127.0.0.1:9000 --hex "de ad be ef"
```

```text
✔ sent 4 bytes → 127.0.0.1:9000
```

`--text` と `--hex` は、どちらか一方だけを指定します。宛先は `IP:port` または `host:port` ([上記](#destinations)) です。終了コードは、データグラムを送信できたときは 0、送信に失敗したときは 1、宛先または hex が無効なときは 2 です。`send tcp` はありません。[コマンドライン](../automation/cli.md#cli-send-udp)を参照してください。

## ストーム {#storm}

[[ui:nav.storm]] は、自分のサーバーや回線のための負荷源です。[[ui:st.udp]] は、指定したサイズのデータグラムを指定したレートで送信し、[[ui:st.tcp]] は、接続を開いてペイロードを書き込んで閉じる、という動作を繰り返します。スループットはリアルタイムで測定されます。[ストーム](../tools/storm.md)を参照してください。

## スキャナー {#scanner}

[[ui:nav.scan]] は、範囲内の各ポートに TCP 接続を試み、接続を受け付けたポートを一覧にします。バナーを要求すると、サービスが最初に返す内容も表示されます。[スキャナー](../tools/scanner.md)を参照してください。

::: danger
ストームとスキャナーは、実在のホストに実際の通信を送ります。所有しているか、テストを許可されているシステムにだけ向けてください。ストームは回線を飽和させることがあり、どちらも侵入検知に引っかかることがあります。
:::

## エミュレートしたデバイス {#emulators}

[[ui:nav.emulators]] 画面では、Signal Lab がデバイスになれます。

- [[ui:emu.new.udp]] は、ペイロードに対するルールでデータグラムに応答します。ルールには、任意、テキストを含む、正規表現に一致する、バイト列を含む、があります。応答は、届いた内容から作るテキストまたは hex で、送信元または別の `IP:port` に、遅延を設定していればその後に送信されます。
- [[ui:emu.new.tcp]] は、接続を受け付け、届いたものを選んだ行末 (LF、CR LF、CR、または届いたチャンクごと) でメッセージに分割し、同じ種類のルールでそれぞれに応答します。クライアントの接続時に挨拶を送ったり、応答のあとに接続を閉じたりもできます。

どちらも、[[ui:exp.node.emulator]] ステップとして、実行の間だけ動かすこともできます。[エミュレーター](../tools/emulators.md)を参照してください。

## 劣化 {#impairment}

[[ui:nav.netsim]] のリレーは、クライアントとその宛先の間に入り、通過するものを劣化させます。UDP ではデータグラムごと (遅延、ロス、重複、順序の入れ替え、帯域制限)、TCP ではストリームごと (遅延、帯域制限、接続のリセットまたはハーフオープンのまま放置) です。[劣化](../tools/impairment.md)と、実験の中では[障害](../experiments/faults.md)を参照してください。

## Windows の「ポートに到達できません」 {#port-unreachable}

データグラムが、何も待ち受けていないポートに届くと、受信側のマシンは通常、ICMP の「ポートに到達できません」メッセージで応答します。Windows は、この応答を、送信したソケットの次の受信で、UDP には接続がないにもかかわらず、接続がリセットされたかのように報告します。

Signal Lab はこれを想定しています。リスナー (OSC モニター、ディスカバリーリスナー、実験の待機と応答、UDP と OSC のエミュレーター、劣化リレー) は、これを記録して待ち受けを続けます。いなくなったデバイスのせいで止まることはありません。本当に受信できなくなったリスナーはジョブを終了し、コンソールに理由が表示されます。

## 問題が起きたとき {#troubleshooting}

| 表示される内容 | よくある原因 |
| --- | --- |
| `… is not a valid address` | 宛先にポートがないか、`IP:port` でも `host:port` でもありません。 |
| `Cannot resolve …` | このマシンでホスト名を名前解決できません。 |
| `… refused the connection — nothing is listening on that port` (TCP) | そのポートで待ち受けているものがないか、ファイアウォールが拒否しています。 |
| `No answer from … in time` (TCP) | ホストがまったく応答しません。アドレスが違うか、拒否ではなく破棄するファイアウォールがあります。 |
| デバイスは応答しているのに、待機がタイムアウトする | デバイスが、待機のポートではなく、データグラムの送信元のポートに応答しています。送信側に [[ui:exp.expectReply]] で応答を待たせてください。そうすると、応答が戻ってくるポートから送信されます。 |
| 他のマシンからのデータグラムがまったく届かない | Windows では、ファイアウォールが遮断していることがあります。アプリが許可を提案したら、Signal Lab を許可してください。[トラブルシューティング](../reference/troubleshooting.md)を参照してください。 |

すべてのエラーメッセージは[エラーメッセージ](../reference/errors.md#transport)に一覧があります。
