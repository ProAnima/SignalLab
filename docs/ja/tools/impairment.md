# 劣化

[[ui:nav.netsim]] 画面は、クライアントとその通信相手の間に入るリレーを動かし、通過するものを双方向で劣化させます。品質の悪い Wi-Fi、モバイル回線、衛星経由、途切れる回線などです。手元にないネットワークで、クライアントやデバイスがどう動作するかを確認するのに使います。

クライアントの向き先を、本物の宛先ではなくリレーにします。リレーは、プロファイルに従って各データグラムやストリームに処理を施したうえで、すべてを宛先に渡し、応答をクライアントに返します。プロファイルは、動作中でもポートを切断せずに変更できます。

## リレーを開始する {#start}

1. [[ui:ns.protocol]] を選びます。データグラム (OSC、ほとんどのショーコントロールやセンサーの通信) なら UDP、ストリーム (HTTP、MQTT、TCP デバイス) なら TCP です。
2. [[ui:ns.listen]] を設定します。リレーが待ち受ける `IP:port` です。`0.0.0.0:9010` はネットワークからの通信を受け付け、`127.0.0.1:9010` はこのコンピューターからだけ受け付けます。
3. [[ui:ns.target]] を設定します。本物の宛先の `IP:port`、または `device.local:9000` のようなホスト名とポートです。
4. [プリセット](#presets)を選ぶか、[プロファイル](#profile)の値を設定します。
5. [[ui:ns.startRelay]] を押します。
6. クライアントの向き先を、宛先ではなくリレーのポートにします。たとえば、`127.0.0.1:9000` ではなく `127.0.0.1:9010` にします。

[[ui:ns.stopRelay]] を押すとリレーが閉じます。それまでに抑えられていたものは、閉じたあとには送信されません。

既定値は、UDP、待ち受け `0.0.0.0:9010`、宛先 `127.0.0.1:9000`、レイテンシ 40 ms、ジッター 15 ms、ロス 2% です。

[[ui:ns.listen]] はバインドするアドレスで、常に `IP:port` です。[[ui:ns.target]] のホスト名は、[[ui:ns.startRelay]] を押したときに一度だけ名前解決されます。これは [OSC](../protocols/osc.md) の宛先と同じです。見つからない名前は拒否され、リレーは開始されません。[[ui:ns.protocol]]、[[ui:ns.listen]]、[[ui:ns.target]] は、リレーの動作中は固定されます。変更するには、いったん停止してください。

```text
client ──► relay (0.0.0.0:9010) ──► target (127.0.0.1:9000)
client ◄── relay ◄───────────────── target
```

### UDP {#udp}

リレーは、各データグラムを専用のポートから宛先に送信し、宛先からの応答をクライアントに返します。各データグラムは、到着したときに決まる、それぞれの運命をたどります。

応答は、最も新しいデータグラムを送信したクライアントに返されます。リレーが一度に相手にするクライアントは 1 つです。

### TCP {#tcp}

クライアントがリレーに張る接続ごとに、リレーが宛先に対して専用の新しい接続を張り、2 つを結びます。各接続の両方向のストリーム (クライアントから宛先、宛先からクライアント) は、リレーが読み取るチャンク単位 (一度に最大 16 KiB) で劣化させられます。ストリームは、ジッターがあっても、常に順序どおりに届きます。

宛先が接続を拒否すると、クライアントの接続はリセットされます。

## プロファイル {#profile}

リレーが双方向に適用する値です。UDP のリレーはデータグラム用の値を、TCP のリレーはストリーム用の値を読み取り、それ以外は非表示になります。

### UDP の場合 {#profile-udp}

| 値 | 動作 | 範囲 |
| --- | --- | --- |
| [[ui:ns.offline]] | チェックを外すまで、両方向のすべてのデータグラムが破棄されます。 | オン / オフ |
| [[ui:ns.latency]] | すべてのデータグラムに加えられます。 | 0〜1000 ms |
| [[ui:ns.jitter]] | データグラムごとに 0 からこの値までのランダムな追加遅延。そのため、データグラムの到着順が入れ替わることがあります。 | 0〜500 ms |
| [[ui:ns.loss]] | 届かないデータグラムの割合。それぞれ独立に判定されます。 | 0〜100% |
| [[ui:ns.burst]] | データグラムがロスのバーストを開始する確率。散発的なロスとは違い、回線が一瞬途切れる状況です。 | 0〜20% |
| [[ui:ns.burstLength]] | 1 回のバーストで失われるデータグラム数の平均。[[ui:ns.burst]] が 0 より大きいときに表示されます。最初に上げたときは 5 です。 | 1〜1000 |
| [[ui:ns.duplicate]] | 2 回配信されるデータグラムの割合。 | 0〜100% |
| [[ui:ns.corrupt]] | 1 バイトの 1 ビットが反転されるデータグラムの割合。 | 0〜100% |
| [[ui:ns.reorder]] | 抑えられるデータグラムの割合。レイテンシの分、最低でも 20 ms 抑えられ、あとに続くものが先に到着します。 | 0〜100% |
| [[ui:ns.rate]] | 帯域制限。キロビット毎秒で指定し、0 は制限なしです。データグラムはこのレートの回線を待つキューに入り、1 秒を超えて待つことになるものは、帯域制限として破棄されます。 | 0、または 8〜10,000,000 |

バーストの仕組みは次のとおりです。バーストの外にあるデータグラムは、[[ui:ns.burst]] の確率でバーストを開始します。バーストの中のデータグラムはすべて失われ、それぞれが 1/[[ui:ns.burstLength]] の確率でバーストを終了します。そのため、バーストは平均でその数のデータグラムの間続きます。

データグラムは、次の順序で処理が決まります。オフライン、バースト、ロス、帯域、そして各コピーについて、重複、破損、遅延、順序入れ替えです。

### TCP の場合 {#profile-tcp}

| 値 | 動作 | 範囲 |
| --- | --- | --- |
| [[ui:ns.offline]] | チェックを外すまで、どちら向きにも何も流れず、新しい接続は宛先を待ちます。チェックを外すと、すべてが再開します。 | オン / オフ |
| [[ui:ns.latency]] | ストリームのすべてのチャンクに、両方向で加えられます。 | 0〜1000 ms |
| [[ui:ns.jitter]] | チャンクごとに 0 からこの値までのランダムな追加遅延。ただし、前のチャンクより先に出ることはありません。 | 0〜500 ms |
| [[ui:ns.reset]] | 通過せずに接続をリセットするチャンクの割合。クライアントと宛先の両方にリセットが届きます。 | 0〜100% |
| [[ui:ns.stall]] | 接続をハーフオープンのままにするチャンクの割合。それ以降は、どちら向きにも何も通過せず、どちらの側にも通知されません。リレーは、停止するまで両側を、手を付けずに開いたままにします。 | 0〜100% |
| [[ui:ns.rate]] | 各接続の各ストリームに対する帯域制限。キロビット毎秒で指定し、0 は制限なしです。キューが 1 秒分を超えると、リレーは読み取りを止め、低速な回線のように送信側が遅くなります。何も破棄されません。 | 0、または 8〜10,000,000 |

ロス、バースト、重複、破損、順序の入れ替えは、TCP には適用されません。本物の TCP ストリームは、失ったものを再送し、自分で順序を整えるので、劣化した回線でクライアントが経験するのは、遅延、送信側の低速化、リセット、応答しなくなる接続です。

::: tip
スライダーは、レイテンシ 1000 ms、ジッター 500 ms で止まります。リレー自体は、たとえば実験ファイルから、それぞれ最大 60,000 ms まで受け付けます。
:::

## プリセット {#presets}

プリセットは、ワンクリックですべての値を設定します。値がプリセットのままである間は、そのチップが点灯し、いずれかの値を変更すると消えます。

| プリセット | UDP の場合 | TCP の場合 |
| --- | --- | --- |
| [[ui:ns.preset.lan]] | 1 ms ±1 | 1 ms ±1 |
| [[ui:ns.preset.wifi]] | 20 ms ±30、ロス 1%、バースト 1% × 3、重複 0.5%、順序入れ替え 2% | 20 ms ±30 |
| [[ui:ns.preset.4g]] | 60 ms ±25、ロス 0.5%、順序入れ替え 0.5%、20,000 kbit/s | 60 ms ±25、20,000 kbit/s |
| [[ui:ns.preset.satellite]] | 300 ms ±30、ロス 1%、2000 kbit/s | 300 ms ±30、2000 kbit/s |
| [[ui:ns.preset.intermittent]] | 30 ms ±20、バースト 3% × 15 | 30 ms ±20、チャンクの 0.2% をハーフオープンのままにする |
| [[ui:ns.preset.offline]] | 何も通らない | 何も流れない |

## 動作中に変更する {#live}

リレーの動作中に、値を変更したり、別のプリセットを選んだりできます。最後の変更から 4 分の 1 秒後に反映され、ポートも接続も切断されません。新しいプロファイルはコンソールに記録され、[[ui:ns.live]] の下の行には、リレーが現在行っていることが表示されます。プリセットの名前、または `60 ms ±25 · loss 2% · 20000 kbps` のような値の要約です。

データグラムやチャンクは、到着した時点で有効なプロファイルで処理が決まります。すでに送出中のものは、その遅延のままです。

## カウンター {#counters}

[[ui:ns.live]] には、リレーが開始してから行った処理が、両方向を合わせて表示され、1 秒に 4 回更新されます。

UDP の場合:

| カウンター | 内容 |
| --- | --- |
| [[ui:ns.received]] | リレーに届いたデータグラム。 |
| [[ui:ns.forwarded]] | 転送したデータグラム。重複したものは 2 回数えます。 |
| [[ui:ns.dropped]] | 意図的に失われたもの。オフライン、バースト、またはロス。 |
| [[ui:ns.throttled]] | 帯域制限によって破棄されたもの。または、すでに 10,000 件 (または 64 MB) が送出中だったために破棄されたもの。 |
| [[ui:ns.duplicated]] | 2 回送信したデータグラム。 |
| [[ui:ns.corrupted]] | ビットを反転させたコピー。 |
| [[ui:ns.reordered]] | あとのものに追い越されるよう抑えたコピー。 |
| [[ui:common.volume]] | 転送したバイト数。 |
| [[ui:ns.notRelayed]] | 該当があるときだけ表示されます。システムが転送しようとしなかったデータグラム。プロファイルによるものではありません。 |

TCP の場合:

| カウンター | 内容 |
| --- | --- |
| [[ui:ns.connections]] | クライアントがリレーに張った接続。 |
| [[ui:ns.received]] | リレーが両方向で読み取ったチャンク。 |
| [[ui:ns.forwarded]] | 書き込んだチャンク。 |
| [[ui:ns.refused]] | 宛先が拒否した、または応答しなかった接続。クライアントにはリセットが届きました。 |
| [[ui:ns.resets]] | リセットした接続。 |
| [[ui:ns.stalled]] | ハーフオープンのままにした接続。 |
| [[ui:ns.held]] | ストリームが帯域制限のために待った回数。送信側は遅くなりましたが、何も破棄されていません。リレーは、すべての接続を合わせて、送出中のデータを最大 64 MB まで保持し、それを超えると同じように待ちます。 |
| [[ui:common.volume]] | 書き込んだバイト数。 |
| [[ui:ns.notRelayed]] | 該当があるときだけ表示されます。このコンピューターが宛先に接続できなかった接続 (ローカルポートやソケットが残っておらず、2 秒間試しても同じだったもの) と、同時に 1,024 を超えた接続。それぞれリセットが返されました。宛先の応答によるものではありません。 |

リレーが自分の側の接続を先に閉じると、ほかのプログラムと同じように、そのあとしばらくの間 (システムの TIME_WAIT)、ローカルポートが保持されます。1 つのリレーを通して 1 秒あたり数百の短い接続を張ると、このコンピューターのポートを使い果たします。するとリレーは待ってから再試行し、それでも通せなかったものは [[ui:ns.notRelayed]] に数えられ、宛先が拒否したものとして扱われることはありません。

キャプチャがオンのときは、[インスペクター](inspector.md)に、リレーされたデータグラムとチャンクが、両方向を合わせて 25 ms に最大 1 件、それぞれの運命とともに表示されます。`forwarded +43ms`、`· corrupted`、`· reordered`、`· copy 2/2`、`dropped (loss)`、`dropped (burst)`、`dropped (offline)`、`throttled`、TCP では `reset` と `half-open` です。→ はクライアントから宛先、← は宛先からクライアントへの向きです。

リレーされたフレームには、実際のソケットが示されます。[[ui:ins.local]] はリレーが待ち受けているアドレス、[[ui:bc.peer]] はそのデータグラムまたはチャンクが向かっていた先で、宛先、または応答が戻されたクライアントです。判定の末尾には、その方向が付きます。`forwarded +43ms · client→target`、`dropped (loss) · target→client` です。そのため、リレーされたデータグラムは [[ui:sig.fromFrame]] で保存でき、向かっていたアドレスが宛先になります。TCP のチャンクはストリームの一部なので、保存できません ([インスペクター](inspector.md#save-as-signal)を参照)。

## 同じ通信なら、同じ運命 {#seed}

すべての判断、つまりどのデータグラムが失われるか、どれだけ遅延するか、どこが破損するかは、リレーのシードから、方向ごとに、TCP では接続ごとに別々に導かれます。同じシードと同じ通信なら、リレーは同じデータグラムを破棄し、同じように遅延させます。

[[ui:nav.netsim]] 画面は、リレーを開始するたびに新しいシードを使います。実行をそのまま再現するには、実験の [[ui:exp.node.impairment]] ノードを使います。このノードは実行のシードから値を導き、そのシードは固定できます ([障害のある実行を再現する](../experiments/faults.md#seed)を参照)。

## 実験での使い方 {#experiments}

2 つのノードで、同じリレーを実験に組み込めます。

- [[ui:exp.node.impairment]] は、最初のステップの前にリレーを開き、実行が終了したときに、終わり方にかかわらず閉じます。待ち受けと宛先のアドレスにはパラメーターだけが使えます。宛先にはホスト名も使え、実行の開始時に名前解決されます。[ノード](../experiments/nodes.md#node-impairment)を参照してください。
- [[ui:exp.node.impairment_change]] は、このステップ以降、実行のリレーを別のプロファイルに切り替えます。クリーン、ロスあり、オフライン、再びクリーン、というように切り替えられ、実行のレポートには、各フェーズが行ったことが数えられます。[ノード](../experiments/nodes.md#node-impairment_change)を参照してください。

OSC または UDP ノードでは、[[ui:exp.routeThrough]] を使うと、その前に [[ui:exp.node.impairment]] が置かれ、ノードの向き先がそのリレーになります。[障害](../experiments/faults.md)を参照してください。
