# 実行の進み方

実行は [[ui:exp.node.start]] から始まり、接続線をたどってノードからノードへ進み、すべてのブランチが終了して [[ui:exp.node.end]] に到達した時点で完了します。このページでは、実行が従うルールを説明します。各ノードが何をするかは[ノードのリファレンス](nodes.md)に、実行とともに流れる値は[データ](data.md)にあります。

## 開始と終了 {#start-end}

実験には、[[ui:exp.node.start]] と [[ui:exp.node.end]] がちょうど 1 つずつあります。

- [[ui:exp.node.start]] には入力がありません。すぐに成功し、タイムラインのその行に実行のシードが表示されます。出力には複数の接続線を引けます。その場合、実験は並列ブランチから始まります。
- [[ui:exp.node.end]] に到達したブランチは、すべてそこで止まります。終了は最初の到達から実行中と表示され、最後のブランチが終わった後に 1 回だけ成功します。どれかのステップが失敗していれば、成功しません。この成功によって、実行が [[ui:exp.passed]] になります。
- すべてのブランチがエラーなしで終了したのに、どれも終了に到達しなかった実行は、`run.no_end` で失敗します。

## 出力と接続線 {#outputs}

ノードのステップは出力を 1 つ選んで終わり、実行はその出力のすべての接続線をたどります。ほとんどのノードの出力は [[ui:exp.outputPort]] の 1 つだけで、いくつかのノードは複数の出力から選びます。

| ノード | 接続が必須の出力 | 接続してもしなくてもよい出力 |
| --- | --- | --- |
| [[ui:exp.node.end]] | — | — |
| [[ui:exp.node.fork]] | [[ui:exp.branch1]]、[[ui:exp.branch2]] | — |
| [[ui:exp.node.branch_status]]、[[ui:exp.node.branch_value]] | [[ui:exp.yes]]、[[ui:exp.no]] | — |
| すべての待機ノード（[[ui:exp.node.wait_osc]]、[[ui:exp.node.wait_udp]]、[[ui:exp.node.wait_mqtt]]、[[ui:exp.node.wait_http]]、[[ui:exp.node.wait_ws]]） | [[ui:exp.portMatched]] | [[ui:exp.portTimeout]] |
| [[ui:exp.node.loop]] | [[ui:exp.portBody]]、[[ui:exp.portDone]] | [[ui:exp.portLimit]] |
| それ以外のすべてのノード | [[ui:exp.outputPort]] | — |

接続するには、出力からノードへドラッグします。何もないキャンバスで離すと、その場所に新しいノードが追加されます。すでに接続線がある出力からドラッグすると、もう 1 本接続線が増えます。[[ui:exp.addNext]]、<kbd>A</kbd> キー、接続線上の ＋ は、既存の接続線の途中にノードを挿入します。

未完成のグラフは下書きです。保存はされますが、実行はされません。ツールバーの [[ui:exp.needsLinks]] に何が足りないかが表示され、該当するノードが示されます。[実行前に何がチェックされるか](#validation)を参照してください。

## 並列ブランチ {#parallel}

### 1 つの出力から複数の接続線 {#fan-out}

出力に複数の接続線があると（[[ui:exp.node.start]] のものも含みます）、それらがつながる先のノードはすべて同時に実行されます。最初の接続線は現在のブランチを続け、2 本目以降の接続線は並列ブランチを開始します。各ブランチは、変数と直近の HTTP レスポンスの独自のコピーを持つので、あるブランチが設定したものや受信したものは、ほかのブランチからは見えません。

### 並列ブランチと合流 {#fork-join}

[[ui:exp.node.fork]] はすぐに成功し、[[ui:exp.branch1]] と [[ui:exp.branch2]] の両方から出ます。1 つの出力から 2 本の接続線を引くのと同じことを、ノードとして描いたものです。

[[ui:exp.node.join]] は、自分に入る**すべての**接続線を待ち、その後、それらの接続線の順にコピーをマージして、1 つのブランチとして続行します。

- すべてのブランチの変数。2 つのブランチが同じ名前を設定した場合は、実験内で後ろに並ぶ接続線が優先されます。
- その順で最後の、レスポンスを持ち込む接続線の HTTP レスポンス。
- その後ろの待機ノードについては、それぞれの直近のアクションのうち最も早いもの。

結果を決めるのは接続線の順序であり、どのブランチがたまたま先に終わったかではありません。

::: warning 並列に実行されるものだけを合流させる
Join は、並列に実行されることになった経緯（[[ui:exp.node.fork]]、1 つの出力の複数の接続線、別々の経路）を問わず、接続線の数を数えます。分岐の [[ui:exp.yes]] と [[ui:exp.no]] の先では片方の経路しか実行されないので、両方から入る Join は、来ることのないブランチを待ち続けます。実行は `run.join_waiting` で失敗し、たどられなかった接続線の数が示されます。代替の経路をまとめるには、それらを次のノードに直接つないでください。
:::

Join ではないノードに 2 つの並列ブランチが到達すると、そのノードはブランチごとに 1 回ずつ実行されます。層を重ねてつなぐと、その数は層ごとに倍になるので、実行が開始できる並列ブランチは合計で 1,000 までです。もう 1 つ開始しようとすると、それを開始するはずだったノードで `run.too_many_branches` により失敗します。そのようなブランチは [[ui:exp.node.join]] でまとめてください。

### ステップが失敗したとき {#failure}

最初の失敗が、実行を失敗にします。ほかのブランチは新しいステップを始めません。繰り返しや負荷は早めに終わり、そのほかの実行中のステップは最後まで実行されます。その間に出会った失敗はタイムラインに報告されますが、実行のエラーにはなりません。[[ui:exp.portTimeout]] の接続線がある状態でタイムアウトになったステップは、失敗していません。[待機](#timeout)を参照してください。

## 分岐 {#branching}

| ノード | [[ui:exp.yes]] から出る条件 |
| --- | --- |
| [[ui:exp.node.branch_status]] | この経路上の直近の HTTP レスポンスが、指定したステータスである |
| [[ui:exp.node.branch_value]] | 比較が成り立つ（[値の比較](data.md#compare)を参照） |

そうでなければ、どちらも [[ui:exp.no]] から出ます。ステータス分岐では、どの経路でもその前に HTTP リクエストが必要で、値による分岐では、読み取る名前がその時点で分かっている必要があります。[[ui:exp.yes]] と [[ui:exp.no]] の先の経路が再び出会う場合、出会うノードは 1 回だけ実行され、そこで分かるのは、両方の経路で設定された変数だけです（[変数が分かる範囲](data.md#visibility)）。

## 再試行 {#retry}

送信または待ち受けを行うステップは、失敗したときにやり直せます。プロパティで [[ui:exp.retryOn]] をオンにします。

| 設定 | 内容 | 範囲 | 最初の値 |
| --- | --- | --- | --- |
| [[ui:exp.attempts]] | 最初の試行を含む、合計の試行回数 | 1〜10 | 3 |
| [[ui:exp.retryDelay]] | 2 回目の試行の前の一時停止 | 0〜60,000 ms | 500 |
| [[ui:exp.backoff]] | [[ui:exp.backoff.fixed]]: どの一時停止も同じ長さ。[[ui:exp.backoff.exponential]]: 各一時停止が前の 2 倍 | — | [[ui:exp.backoff.fixed]] |

- 再試行は、[[ui:exp.node.http]]、[[ui:exp.node.tcp]]、[[ui:exp.node.mqtt]]、[[ui:exp.node.osc]]、[[ui:exp.node.udp]]、[[ui:exp.node.ws_connect]]、[[ui:exp.node.ws_send]]、およびすべての待機ノードに適用されます。ほかのノードでは拒否され（`node.retry_unsupported`）、[負荷](load.md)をかける HTTP リクエストには再試行を設定できません。
- 倍増しても、1 回の一時停止が 60 秒を超えることはありません。
- 失敗した試行は、番号と理由とともに、タイムラインに [[ui:exp.retry]] として表示されます。その後、ステップは成功するか、最後の試行の理由で失敗します。
- 繰り返されるのは実行だけです。テンプレートが解決できないフィールドは、すぐに失敗します。
- 応答を待つ送信は、もう一度送信します。待機ノードは、これまでと同じくブランチの直近のアクションから数えて、もう一度待ちます。
- [[ui:exp.portTimeout]] の接続線がある待機ノードは、タイムアウトしても失敗しないので再試行されません。[[ui:exp.portTimeout]] に従って進みます。
- [停止](#stop)は、一時停止をすぐに終了させます。

## 繰り返し {#repeat}

送信するステップは、グラフにループを置かなくても、ハートビート、ポーリング、一定のストリームのように、繰り返し送信できます。[[ui:exp.repeatOn]] をオンにします。

| 設定 | 内容 | 範囲 | 最初の値 |
| --- | --- | --- | --- |
| [[ui:exp.repeatBy]] | [[ui:exp.repeatBy.count]] または [[ui:exp.repeatBy.duration]] | — | [[ui:exp.repeatBy.count]] |
| [[ui:exp.repeatCount]] | 最初の送信を含む、合計の送信回数 | 2〜10,000 | 10 |
| [[ui:exp.repeatDuration]] | 最初の送信から、送信を続ける時間 | 1〜300,000 ms | 10,000 |
| [[ui:exp.repeatInterval]] | 2 回の送信の間の一時停止 | 10〜60,000 ms | 1000 |
| [[ui:exp.repeatJitter]] | 各一時停止に、ランダムにこの値までの時間が加わります | 0〜60,000 ms | 0 |

- 繰り返しは、[[ui:exp.node.http]]、[[ui:exp.node.tcp]]、[[ui:exp.node.mqtt]]、[[ui:exp.node.osc]]、[[ui:exp.node.udp]]、[[ui:exp.node.ws_send]] に適用されます（ほかのノードでは `node.repeat_unsupported`）。HTTP リクエストに設定できるのは、繰り返しか[負荷](load.md)のどちらかで、両方は設定できません。
- 各送信は、単独の送信と同じように行われます。テンプレートは読み直され（`{{counter}}` はその送信の番号、`{{now}}` はその時刻）、再試行が有効な場合は送信ごとに適用されます。応答を待つ送信は、それぞれの応答を待ちます。
- 時間を指定した場合、送信は、時間が尽きる前に開始できるときだけ行われます。
- ジッターは実行のシードから決まるので、同じシードなら同じ一時停止になります。
- タイムラインには、進行状況が [[ui:exp.repeating]] として、1 秒に 1 回までの頻度で表示されます。ステップは最後の送信の後に、その送信の結果で成功し、最終的に失敗した送信があればステップは失敗します。
- 別のブランチでの失敗は、送信を終わらせます。[停止](#stop)は、一時停止をすぐに終了させます。

繰り返しは 1 回の実行に収まっていなければなりません。送信とその最長の一時停止（`(count − 1) × (interval + jitter)`）は最大 300 秒（`node.repeat_too_long`）、時間を指定した繰り返しは最大 10,000 回の送信（`node.repeat_too_many`）です。

## ループ {#loop}

[[ui:exp.node.loop]] は、その [[ui:exp.portBody]] 出力にあるステップを繰り返し実行します。その最後のステップは、ループに接続し返されます。

| 設定 | 内容 | 範囲 |
| --- | --- | --- |
| [[ui:exp.loopMax]] | 最大の反復回数 | 1〜1000 |
| [[ui:exp.loopUntilOn]] | 終了条件: [[ui:exp.value]]、[[ui:exp.operator]]、[[ui:exp.expected]]。[[ui:exp.node.assert_value]] と同じです | 任意 |

1. 外側から到達すると、ループは [[ui:exp.portBody]] で反復 1 を開始します。
2. 本体が戻ってくるたびに、終了条件が読まれます。反復の後に読まれるので、本体は少なくとも 1 回は必ず実行され、条件で調べる値を本体が設定することもできます。
3. 条件が成り立つと、ループは [[ui:exp.portDone]] から出ます。
4. そうでなければ、反復が残っている限り、次の反復が始まります。
5. 先に反復回数が尽きた場合、ループは、[[ui:exp.portLimit]] に接続線があればそこから出て、なければ `loop.limit` で実行を失敗させます。条件がない場合、本体はすべての反復を実行し、ループは [[ui:exp.portDone]] から出ます。

本体の中では、すべてのノードが自分の実行回数を数えるので、`{{counter}}` は反復の番号です。条件と、[[ui:exp.portDone]] または [[ui:exp.portLimit]] の後のステップは、本体のすべての反復が設定するもの（たとえば本体が抽出するステータス）を使えます。一方、本体自身から見えるのは、ループに到達した時点で分かっていたものだけです。

テンプレート [[ui:exp.templatePoll]] は、デバイスが `ready` と答えるまで、0.3 秒ごとにステータスを尋ね、最大 10 回繰り返します。

### 本体に置けるもの {#loop-body}

本体は 1 つのブランチとして、反復を 1 回ずつ順に実行します。ループへ戻る接続線は、実験に含められる唯一のサイクルで、それ以外は `graph.cycle` になります。

| ルール | エラー |
| --- | --- |
| [[ui:exp.portBody]] にあるものがループへ戻る | `loop.no_return` |
| 本体の各出力に接続線が 1 本ある | `loop.body_parallel` |
| 本体のすべての出力が、本体の中でさらに進むか、ループへ戻る | `loop.body_leaves` |
| ループの [[ui:exp.portBody]] 出力だけが本体に入る | `loop.body_entered` |
| 本体に [[ui:exp.node.start]]、[[ui:exp.node.end]]、[[ui:exp.node.fork]]、[[ui:exp.node.join]]、ほかの [[ui:exp.node.loop]] がない | `loop.body_unsupported` |

## 待機 {#waits}

待機ノードは、待っているメッセージが届くと成功します。[[ui:exp.node.wait_osc]]、[[ui:exp.node.wait_udp]]、[[ui:exp.node.wait_mqtt]]、[[ui:exp.node.wait_http]]、[[ui:exp.node.wait_ws]] です。それぞれが何に一致するかは[ノードのリファレンス](nodes.md)にあります。ここでは、どのように待ち受けるかを説明します。

### 最初から待ち受ける {#listening}

実行は、待機ノードが待ち受けるものを**最初のステップの前に**開くので、次のステップより速い応答も取りこぼしません。

| 待機 | 最初のステップの前に開かれるもの |
| --- | --- |
| OSC、UDP | [[ui:exp.listenOn]] のアドレスごとに 1 つの UDP ソケット。そのアドレスのすべての待機ノードが共有します |
| HTTP リクエスト | アドレスごとに 1 つのリスナー。実行の HTTP [エミュレーター](faults.md#emulator)があればそれ、なければ `204` で答えるリスナー |
| MQTT | ブローカーとトピックフィルターごとに 1 つの接続（サブスクライブ済み）。ブローカーが再送する保持メッセージは無視されます |
| WebSocket | なし: [[ui:exp.node.ws_connect]] が実行時に開いた接続を読みます |

これらは最初に開かれるため、アドレスは実行の前に決まっています。OSC、UDP、HTTP の待機ノードは、ポートが 0 以外の、リテラルの `IP:port` で待ち受け、MQTT の待機ノードのブローカーとトピックにはパラメーターしか使えません。開けないポート（使用中、またはこのコンピューターのアドレスではない）があると、トラフィックが発生する前に、その待機ノードのフィールドで実行が止まります。すべては、実行がどのような形で終わっても、終了時に閉じられます。

### 数えられるメッセージ {#counting}

待機ノードが対象にするのは、**ブランチ上の直近のアクション**（直近のリクエスト、メッセージ、パブリッシュ、WebSocket の接続や送信）が始まった後に届いたメッセージです。アクションがまだなければ、実行が始まった後に届いたものです。リクエストより前のメッセージは数えられず、リクエストと待機の間にある Delay やログがその応答を隠すこともありません。Join の後では、マージされたブランチの直近のアクションのうち最も早いものから数えます。

待機ノードは、最初に一致したメッセージを採用して消費します。2 つの待機ノードが同じメッセージに一致することはありません。

各ソケット、サブスクリプション、接続は、待機ノードのために最大 1024 件のメッセージと 64 MiB を保持します。それを超えると、最も古いものから破棄され、数えられます。

### タイムアウト {#timeout}

[[ui:exp.waitTimeout]] は 1〜120,000 ms で、最初は 2000 です。時間内に何も一致しなかった場合は次のようになります。

- [[ui:exp.portTimeout]] に接続線があれば、待機ノードはそちらに従って進みます。
- なければ、ステップは `wait.timeout` で失敗します。これには、その間にほかに何件のメッセージが届いたかが示され（パターンの誤りとデバイスの無反応は区別できます）、詳細には、キューが満杯のときに何件の古いメッセージが破棄されたかが示されます。

待機ノードの変数（`reply`、HTTP では `request`）は、[[ui:exp.portMatched]] の後にだけ存在します。[[ui:dock.inspector]]がキャプチャしているときは、ステップに、一致したフレームへのリンクも付きます。[タイムライン](runs.md#timeline)を参照してください。

## 同じステップでの応答 {#reply}

[[ui:exp.node.osc]] や [[ui:exp.node.udp]] は、自分への応答を待てます。[[ui:exp.expectReply]] をオンにします。

| 設定 | 内容 | 最初の値 |
| --- | --- | --- |
| [[ui:exp.replyOn]] | 応答を待ち受けるアドレス。ポート 0 は空いている任意のポート | `0.0.0.0:0` |
| [[ui:exp.replyAddress]] (OSC)、[[ui:exp.replyMode]] (UDP) | 応答が満たすべき条件。対応する待機ノードと同じです | 任意 |
| [[ui:exp.waitTimeout]] | 1〜120,000 ms | 2000 |
| [[ui:exp.replyVariable]] | 応答を書き込む変数 | `reply` |

[[ui:exp.replyOn]] のソケットは、待機ノードのものと同じく、最初のステップの前に開かれ、メッセージは**そこから送信されます**。送信元自身のポートに返答するデバイスの応答が受け取れ、固定のポートに返答するデバイスの応答は、そのポートを指定したときに受け取れます。ステップは、一致する応答があれば成功し、変数はその出力の後に存在します。[[ui:exp.portTimeout]] 出力はありません。時間内に応答がないとステップは失敗し、再試行を設定していれば再送信できます。無音で分岐したいときは、別に待機ノードを使ってください。

## 実行前に何がチェックされるか {#validation}

エディターは、編集中に実験をチェックし、実行ボタンがもう一度チェックします。問題は、ノードと、あればフィールドを示します。

| ルール | エラー |
| --- | --- |
| 実験に名前がある | `doc.name_required` |
| ノードが 1〜64 個で、開始と終了がちょうど 1 つずつ | `doc.node_count`、`doc.start_end_count` |
| 開始に入力がない | `graph.start_input` |
| 接続線が、存在する別のノードにつながっている | `doc.connection_invalid` |
| 同じ接続線が 2 本ない | `doc.connection_duplicate` |
| 接続が必須の出力がすべて接続されている | `graph.outputs_required` |
| ノードに、持っていない出力の接続線がない | `graph.port_unexpected` |
| すべてのノードが開始から到達できる | `graph.unreachable` |
| ループへ戻る接続線以外にサイクルがない | `graph.cycle`、および[本体のルール](#loop-body) |
| チェックまたは抽出の前に、すべての経路で HTTP リクエストがある（負荷をかけたリクエストは数えない） | `graph.needs_http` |
| すべてのテンプレートが解析でき、使われるすべての名前がすべての経路で分かっている | `template.*`、`name.*`（[データ](data.md#unknown-names)を参照） |
| すべてのフィールドが存在し、範囲内にある | `node.*` |
| ほかのノードを名前で指すノード（[[ui:exp.node.impairment_change]]、[[ui:exp.node.emulator_state]]、WebSocket ノード）が、存在するノードを指し、WebSocket ノードがその接続ノードより後にある | `impair.relay_unknown`、`emulator.node_unknown`、`ws.connection_unknown`、`ws.connection_after` |
| 実行内の 2 つのソケットがポートを共有していない | [障害](faults.md#ports)を参照 |

その後、実行は、開始に必要なものをチェックします。すべての[シークレット](data.md#secret-check)が保存されていること、すべてのポートが開けることです。すべてが満たされるまで、ステップは実行されず、何も送信されません。

## 時間制限 {#limit}

実行は最大 300 秒です。それを過ぎても続いている実行は停止され、`run.timeout` で失敗します。[コマンドライン](../automation/cli.md#cli-run)と [API](../api/run.md) からは、制限をもっと短く、1〜300 秒に設定できます。

## 停止 {#stop}

実行中は、実行ボタンが [[ui:common.stop]] になります。停止は、実行を直ちに終了させます。すべてのブランチ、再試行や繰り返しのすべての一時停止、すべての待機、すべての負荷が対象で、送信中のリクエストは破棄されます。ソケット、サブスクリプション、エミュレーター、リレーは閉じられ、WebSocket の接続はクローズフレームを送ります。ヘッダーの [[ui:app.stopAll]] は、すべてのジョブに対して同じことを行います。停止された実行はレポートを保存しません。[実行](runs.md#stop)を参照してください。
