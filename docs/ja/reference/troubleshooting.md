# トラブルシューティング

Signal Lab が報告する失敗にはすべてコードがあり、それぞれのメッセージは[エラーメッセージ](errors.md)にあります。ネットワークの失敗は [`transport`](errors.md#transport) のコードで、`refused`、`timeout`、`dns`、`unreachable`、`reset`、`address_in_use`、`address_unavailable`、`denied`、`tls`、`target_invalid`、`exhausted`、`failed` です。以下は、よくある問題です。

## 何も届かない {#nothing-arrives}

まず、そもそも何かが Signal Lab に届いているかを確認します。下部パネルの [[ui:dock.inspector]] タブを開き、[[ui:ins.arm]] を押してください。ツールが送受信するすべてのデータグラム、リクエスト、メッセージが、送信元とともに一覧表示されます。

### 待ち受けアドレス {#listen-address}

- [[ui:common.bind]] が `0.0.0.0:<port>` ならすべてのネットワークカードで待ち受け、`127.0.0.1:<port>` ならこのマシンの通信だけが聞こえます。ネットワーク上の機器からの通信には、前者が必要です。
- デバイスは、このマシンのアドレスと、待ち受けているポートに送信する必要があります。このマシンの名前とアドレスは、ヘッダーに表示されています。
- このマシンのものではないアドレスは、`address_unavailable` で失敗します。

### ファイアウォール {#firewall}

`127.0.0.1` の通信は、決してフィルターされません。そのため、1 台のマシン内のテストは動くのに、同じテストを別のマシンから行うと何も届かない、ということが起こります。

**Windows。** Windows ファイアウォールは、プログラムごとに判断します。通常、Windows は、プログラムが最初に待ち受けを始めたときに一度だけ確認を求めます。そこで「キャンセル」を選ぶと、それをブロックする規則が残り、どの許可規則よりも優先されます。Windows がパブリックと見なすネットワーク (会場の Wi-Fi は多くがこれです) では、確認がまったく表示されないこともあります。

- デスクトップアプリは、モニター、ディスカバリーリスナー、リレー、実行、エミュレーターが待ち受けを開始したときに、一度だけファイアウォールを確認します。ファイアウォールが妨げている場合は、[[ui:fw.allow]] (パブリックネットワークでは [[ui:fw.allowPublic]]) 付きの通知でそれを伝えます。Windows が管理者権限を求め、そのプログラムの受信規則 (ブロック規則を含む) が、1 つの許可規則に置き換えられます。[[ui:fw.dismiss]] で通知を非表示にできます。
- ターミナルからは、`signallab doctor` で妨げているものがわかり、`signallab firewall allow` で修正できます (パブリックネットワークでも許可するには `--public`)。管理者権限の確認は同じように表示されます。
- *すべてのユーザー向け*にインストールしたセットアップ (`.exe`) は、`/NOFIREWALL` で実行しない限り、許可規則を自分で追加します (プライベートとドメインのネットワーク)。*自分用*のセットアップにはそれができず、`.msi` はファイアウォールの設定を、展開する人に任せます。
- サーバーは、ホストのファイアウォールを変更しません。ポートは、サーバーの管理者が開けます (インストールスクリプトは、ufw または firewalld で開けることを提案します)。

**Linux。** ufw や firewalld などのファイアウォールは、プログラムではなくポートで動作します。`signallab doctor` は、有効になっているファイアウォールと、ポートの開け方 (たとえば `sudo ufw allow 9000/udp`) を示します。

### ブロードキャストとマルチキャスト {#broadcast-multicast}

- ルーターはブロードキャストを転送しません。`255.255.255.255` と `x.x.x.255` は、送信するカードがあるネットワークセグメントにしか届きません。カードが複数ある場合は、[[ui:bc.bindSource]] ([[ui:bc.socketOptions]] の下) にカードのアドレスを入力してください。たとえば `10.0.0.5:0` です。
- マルチキャストのデータグラムは、そのグループに参加しているリスナーにしか届きません。ディスカバリーリスナーでは [[ui:bc.joinGroups]] です。[[ui:bc.ttl]] が既定の 1 だと、このネットワークの外には出ません。
- 同じマシンで自分のマルチキャストを聞くには、[[ui:bc.mcastLoop]] をオンのままにします。

### 応答しないデバイス {#no-answer}

UDP には配達確認がありません。誰も待ち受けていないポートに送信したデータグラムも、送信済みとして数えられます。Windows は、そのとき返ってきた ICMP の*ポートに到達できません*というメッセージを、そのソケットの次の受信で、接続のリセットとして報告します。Signal Lab のモニター、リスナー、リレー、待機はそれを無視して、待ち受けを続けます。そのため、応答が来ない場合、待機は、送信に関するエラーではなく、その時間が過ぎたあとに `wait.timeout` で失敗します。[[ui:dock.inspector]] で、メッセージが正しいアドレスに送信されたかを確認してから、デバイスを調べてください。

## 送信が、送信前に拒否される {#refused-send}

これらは最初にチェックされ、どれかが失敗すると何も送信されません。

| コード | 理由 | 対処 |
| --- | --- | --- |
| `transport.target_invalid` | 宛先にポートがないか、`IP:port` でも `host:port` でもありません | 両方を書いてください。たとえば `192.0.2.20:9000` |
| `transport.dns` | このマシンでホスト名を名前解決できません | 名前を確認するか、アドレスを使ってください。IPv4 アドレスを持つ名前は IPv4 で接続するので、`localhost:9000` は `127.0.0.1` の受信側に届きます |
| `node.osc_address` | OSC アドレスが `/` で始まっていません。送信側、ジェネレーター、シグナル、ステップのいずれでも | `/cue/go` のように、`/` で始めてください |
| `node.topic_wildcard` | MQTT のパブリッシュのトピックに `+` または `#` が含まれています。画面の接続でも、ほかのどこでも同じです | 1 つのトピックにパブリッシュしてください。ワイルドカードはサブスクライブ用です |
| WebSocket メッセージでの `node.too_long` | メッセージが 16 MiB を超えています | 小さくして送信してください。接続は開いたままです |

## ポートがすでに使用中 {#port-in-use}

`transport.address_in_use`: ほかのプログラム、または Signal Lab の別のジョブが、すでにそのポートで待ち受けています。

- **モニターと実行。** 実行は、最初のステップの前に、待機、エミュレーター、リレーのポートを開きます。そのため、[[ui:osc.monitor]]、ディスカバリーリスナー、エミュレーターのジョブがポートを使っていると、実行は開始前に失敗します。先にそのジョブを停止してください。[[ui:app.stopAll]] はすべてを停止します。
- 実行内の**2 つのエミュレーター**は、1 つのトランスポートのポートを共有できません。HTTP、MQTT、TCP のエミュレーターはすべて TCP で、OSC と UDP のエミュレーターは UDP で待ち受けます (`emulator.bind_taken`)。
- **本物のサービスと並べて待ち受ける。** ディスカバリーリスナーは、すでにそのポートを使っているプログラムとポートを共有できます。[[ui:bc.reuse]] をオンのままにしてください。Linux では、そのプログラム側もポートを共有する設定が必要です。共有しないと、使用中のポートは `broadcast.port_shared` になります。
- **停止した直後。** 停止したエミュレーターや実行が使っていたポートは、少しあとに解放されます。すぐに再起動したエミュレーターは、それを短時間待ちます。
- Linux では、**1024 未満のポート**には管理者権限が必要です (`denied`)。サーバーのイメージは権限なしで動作するので、1024 以上のポートを使ってください。

## Docker のサーバーがネットワークに届かない {#docker-network}

ブロードキャスト、マルチキャスト、ディスカバリーが物理ネットワークに届くのは、ホストネットワークを使う場合、つまり compose ファイルの `network_mode: host` か `docker run --network host` で、しかも Linux ホストのときだけです。これにより、モニター、待機、エミュレーターも、ホスト自身のポートで待ち受けられます。Docker の既定のブリッジネットワークでは、コンテナは専用のネットワーク上にあり、ブロードキャストとマルチキャストはそこから出ず、公開したポートだけが届きます。

Windows と macOS では、Docker のホストネットワークは物理ネットワークに届きません。Windows ではデスクトップアプリを使うか、Linux ホストでサーバーを動かしてください。

## SmartScreen がインストーラーについて警告する {#smartscreen}

インストーラーにはまだ署名がないため、Windows SmartScreen は発行元を知らないと表示します。「詳細情報」を選び、「実行」を選んでください。インストーラーは、GitHub のプロジェクトのリリースからだけダウンロードしてください。

## サーバーが起動しない {#server-start}

`signal-lab-server` は、待ち受けの前に設定を確認し、エラー出力にメッセージを出して終了します。

| 終了コード | メッセージ | 対処 |
| --- | --- | --- |
| 2 | refusing to listen on … without a token | 他者が到達できるサーバーにはトークンが必要です。`--token-file` または `SIGNALLAB_TOKEN` (`signal-lab-server token` で作れます)、または `--generate-token` を使ってください。または `127.0.0.1` で待ち受けてください |
| 2 | the token has N characters; it needs at least 24 | もっと長いトークンを使ってください |
| 2 | the token must not contain spaces or line breaks | トークンファイルの末尾の改行は許されますが、それ以外は不可です |
| 2 | give the token once | `--token`/`SIGNALLAB_TOKEN` か `--token-file`/`SIGNALLAB_TOKEN_FILE` のどちらか一方だけを使ってください |
| 2 | --generate-token keeps the token in the data folder | `--data-dir` または `SIGNALLAB_DATA_DIR` を設定してください |
| 2 | … it does not hold a valid token; remove it to have a new one made | データフォルダーの `token` ファイルが壊れています |
| 2 | cannot read the token file … | `--token-file` で指定したファイルがないか、このユーザーが読み取れません |
| 2 | cannot save the new token in … | `--generate-token` が、データフォルダーに `token` を書き込めませんでした。このユーザーが書き込めるフォルダーにしてください |
| 1 | cannot listen on … | アドレスがこのマシンのものでないか、ポートが使用中です |
| 1 | the data folder … must be writable by this user | Docker では、バインドマウントしたフォルダーは uid 10001 が書き込める必要があります |

`--generate-token` が作ったトークンは、最初の起動時に一度だけ表示され (`docker logs signallab` で確認できます)、データフォルダーの `token` に保持されます。`docker exec signallab cat /data/token` で読めます。[サーバー](../server/index.md)を参照してください。

## サーバーにサインインできない {#sign-in}

| 表示される内容 | 理由 | 対処 |
| --- | --- | --- |
| *トークンが正しくありません。* | トークンが間違っています | サーバーが保持している場所から、もう一度コピーしてください。応答に 1 秒かかるのは仕様です |
| `auth.host` | アドレスバーの名前に、サーバーが応答しません | サーバーが受け付ける名前で開いてください。ループバックの名前 (`localhost`、`127.x.x.x`、`[::1]`) は常に通ります。トークンがないサーバーは、それらと `--allowed-host` の名前にだけ応答します。トークンがある場合は、`--allowed-host` で絞り込まない限り、どの名前にも応答します |
| `auth.origin` | 別のオリジンのページからリクエストが来ました | リバースプロキシの背後では、ブラウザーの `Host` をサーバーに渡してください (nginx では `proxy_set_header Host $host;`)。`Origin` と `Host` が一致するようにします |
| サインインしたのに、サインインページに戻る | ブラウザーがセッション Cookie を保持しませんでした | `--secure-cookie` を使う場合は、サーバーに HTTPS で接続する必要があります |
| しばらくすると、サインアウトされる | セッションは 7 日間有効で、サーバーの再起動で終了します。1024 セッションを超えると、最も古いものが消えます | もう一度サインインしてください |

## サーバーとの接続が切れ続ける {#connection-lost}

[[ui:app.connectionLost]] は、ページのイベントソケット `/api/events` が閉じたことを意味します。ページは、0.5 秒後に、その後は間隔を延ばしながら、最長 15 秒おきに自動で再接続します。その間に起きたことは再送されません。実行中のジョブは、続行しながら改めて報告します。リバースプロキシの背後では、`/api/events` の WebSocket アップグレードを通し、静かな接続を 20 秒未満で閉じないようにしてください (サーバーは 20 秒ごとに ping を送ります)。サーバーにそのようなアドレスはないと表示されるページ (`api.not_found`) は、サーバーより古いものです。再読み込みしてください。

## MQTT に接続できない {#mqtt}

Signal Lab が話すのは、プレーン TCP 上の MQTT 3.1.1 です。接続して、ブローカーの応答 (CONNACK) を待ってから成功を報告するので、理由は接続ボタンに表示されます。

| コード | 理由 | 対処 |
| --- | --- | --- |
| `transport.refused` | そのポートで待ち受けているものがありません | ポートを確認してください。通常は 1883 です |
| `transport.timeout` | 6 秒以内に TCP 接続できませんでした | アドレス、ネットワーク、ブローカーのファイアウォールを確認してください |
| `transport.dns` | ホスト名を名前解決できません | 名前を確認するか、アドレスを使ってください |
| `transport.unreachable` | ブローカーへの経路がありません | ネットワークとアドレスを確認してください |
| `transport.reset` | ブローカーが接続をすぐに閉じました | TLS のポート (8883) であることが多いです。Signal Lab は TLS 上の MQTT を話しません |
| `mqtt.no_answer` | ポートは開いていますが、6 秒以内に CONNACK が来ませんでした | WebSocket のポートであることが多いです。Signal Lab は WebSocket 上の MQTT を話しません |
| `mqtt.protocol` | 応答したものが MQTT ブローカーではありません | ポートを確認してください |
| `mqtt.refused_protocol` | ブローカーが MQTT 3.1.1 を受け付けません | ブローカーで 3.1.1 を有効にしてください |
| `mqtt.refused_client_id` | ブローカーがクライアント ID を拒否しました | 別のクライアント ID を使ってください |
| `mqtt.refused_unavailable` | ブローカーが利用できません | あとでもう一度試してください |
| `mqtt.refused_credentials` | ユーザー名またはパスワードが間違っています | 確認してください |
| `mqtt.refused_not_authorized` | そのユーザーは接続を許可されていません | ブローカーのアクセスルールを確認してください |
| `mqtt.client_id_required` | クライアント ID が空です | 入力してください |

ブローカーは、同じクライアント ID の 2 つの接続のうち古いほうを切断します。接続が閉じ続ける場合は、同じ ID を使っている別のクライアントがないか確認してください。

## 証明書が信頼されない {#tls}

`https://` または `wss://` での `transport.tls`: サーバーの証明書が信頼されていないか、要求したホストの名前を含んでいないか、TLS の合意ができませんでした。Signal Lab は、システムと同じ方法で証明書を検証し、その検証を省略する切り替えはありません。HTTPS と WSS は同じ証明書を信頼します。エンジンが動作するオペレーティングシステムの証明書、つまり Windows では Windows の証明書ストア、Linux とサーバーのイメージではシステムの CA 証明書です。自己署名証明書や独自の CA を使う場合は、そのマシンの信頼済み証明書に追加してください (サーバーのイメージでは、そのイメージをもとに証明書を追加したイメージをビルドします)。接続は、証明書に書かれている名前で行ってください。

## シークレットがない {#secrets}

`secret.missing`: 実験が `{{secret.NAME}}` を使っていて、実行される場所に、その名前で保存された値がありません。

- **Windows のデスクトップアプリ**: エディターの [[ui:exp.params]] の [[ui:exp.secrets]] で設定します。値は Windows 資格情報マネージャーに保持されるので、新しいマシンでは設定し直す必要があります。
- **サーバー**: ファイル `/run/secrets/signallab/NAME` (または `--secrets-dir` で指定したフォルダー) に値を置くか、環境変数 `SIGNALLAB_SECRET_NAME` に設定します。サーバーは、ページからシークレットを設定できません (`secret.read_only`)。
- **Linux のデスクトップアプリ**には、シークレットを保存する場所がありません (`secret.unsupported`)。そのような実験は、ファイルと環境変数からシークレットを読み込む `signallab run` で、またはサーバーで実行してください。

[ファイル](files.md#secrets)を参照してください。

## 実行が 5 分で止まる {#run-timeout}

300 秒を超えた実行は `run.timeout` で失敗します。これが 1 回の実行にかけられる最長の時間です。これより短い制限は、API (`timeout`、[`/api/run`](../api/run.md#request)) またはコマンドライン (`signallab run --timeout`) で、実行ごとに指定できます。

## アプリが更新されない {#updates}

- デスクトップアプリは、[[ui:update.auto]] がオンの間は 1 日 1 回、また [[ui:about.open]] で [[ui:update.check]] を押したときに、新しいバージョンを確認します。
- まずスタジオのハブに問い合わせ、ハブに到達できないときは GitHub に問い合わせます。ネットワークがその両方を遮断している場合、[[ui:update.check]] は [[ui:update.checkFailed]] を表示し、毎日の確認は何も表示せずに失敗します。
- 提供されるのは、公開されたリリースだけです。ドラフトやプレリリースは対象外です。
- 新しいリリースがアプリに届くのは、ハブがそれを提供したときで、GitHub に現れてからしばらくあとになることがあります。ハブは、一度に一部のインストールにだけリリースを展開します。
- インストールされるのは、[[ui:update.install]] を押したときだけです (実行中のジョブは先に停止されます)。署名が検証できるリリースに限られ、そうでなければ [[ui:update.installFailed]] になります。
- サーバーは、イメージで更新します。compose ファイルのフォルダーで `docker compose pull && docker compose up -d` を実行してください。

## ログの場所 {#logs}

- **デスクトップアプリ**: ログファイルは書き込みません。下部パネルの [[ui:console.title]] タブに、各ツールが行ったことと、うまくいかなかったことが一覧表示され、[[ui:feedback.open]] はそれを (このコンピューターの名前、アドレス、あなたのフォルダーを除いて) 開発者へのメッセージに添付します。各実行のレポートは、データフォルダーの `runs/` にあります。
- **サーバー**: 標準出力と標準エラー出力にログを出します。Docker では `docker logs signallab` です。ジョブの開始は、要求したクライアントのアドレスとともに、すべて記録されます。`--log` (または `SIGNALLAB_LOG`) でレベルを設定します。`error`、`warn`、`info` (既定)、`debug` のいずれかです。`--log-format json` (または `SIGNALLAB_LOG_FORMAT`) は、1 行に 1 つの JSON オブジェクトを出力します。
- **コマンドライン**: `signallab` は、メッセージをエラー出力に書き込みます。[コマンドライン](../automation/cli.md)を参照してください。
